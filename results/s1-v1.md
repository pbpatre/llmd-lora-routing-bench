# S1 baseline, v1 (9 Nov 2026)

S1 replicates the starvation study in llm-d-router#3392:
- 4 pods, `--max-loras 2`, `--max-cpu-loras 16`;
- 2 hot adapters (90% of LoRA traffic) and 4 cold ones;
- 20% base-model traffic;
- 12 req/s, 256 output tokens, 180 s, with the steady window after 60 s.

## Setup

| | |
| --- | --- |
| GPUs | 4× NVIDIA B200 (one pod each), driver 580.178.04 |
| vLLM | 0.31.0, `unsloth/Llama-3.1-8B-Instruct@4699cc75`, synthetic rank-16 adapters |
| Router | llm-d-router `1f7f0d90` (#3392 merge), file discovery behind Envoy 1.33.2 |
| Runs | 4 arms × seeds 1–3, plus an A/A repeat of `residency-w4` per seed; 15 valid runs |
| Calibration | S0 on one B200 pod (below) |

Every reported run passed all validity checks (DESIGN_LLMD_709.md §6.4):
- client loop lag p99 about 1 ms, send lag p99 about 1.5 ms;
- every request decoded exactly 256 tokens;
- every request attributed through Envoy's access log, with the response header agreeing;
- no errors or Envoy overflow;
- vLLM load lines parsed;
- base-model TTFT within 3× of the unloaded p99.

## Findings

1. **The starvation regime reproduces; the size doesn't.**
   - Under stock, cold p99 is 2.1–3.3 s, against 0.03 s under residency.
   - Most cold requests (62–73%) arrive at a pod whose two slots are both held by other adapters.
   - #3392 reported 6.95–7.73 s vs about 0.2 s on 4×H100.
   - The ratio is similar; the absolute wait is shorter on B200.
2. **The wait is queueing for a slot, not loading.** An activation costs about 12 ms, yet cold requests wait seconds under stock. They queue behind hot adapters holding both slots.
3. **The prefix-cache scorer isn't the cause.** Removing it (`stock-noprefix`) changes cold p99 by less than the seed-to-seed spread.
4. **On this rig, `lora-affinity-scorer` also removes starvation** (cold p99 0.04 s), with about 80 activations per run against residency's 4.
5. **Packing has a cost.** Residency puts each adapter on one pod, so the busiest pod carries 1.5–1.7× the mean in-flight load (stock: about 1.03×). In S1, compute fits, so it doesn't hurt latency. S3 and S4 test the case where it doesn't fit.

## Open points

- **The capacity rule.** The v2.2 rule's ITL condition (≤ 1.3× unloaded) fired well before TTFT jumped, because inter-token latency rises gradually with batch size: 6 req/s at L = 1024, while TTFT breaks only between 16 and 20. DESIGN_LLMD_709.md v2.3 uses the highest rate with TTFT p99 ≤ 4× unloaded (§12), which S3 and S4 scale from. S1 uses a fixed rate, so it is unaffected.
- **Parameters assumed** (not stated in #3392): adapter rank 16, `--max-lora-rank 16`, prompt length 64 words.
- **Not yet checked automatically:** the residency response hook, the EPP plugin-latency bound, and GPU throttling.
- **The cold (unprimed) variant of #3392's S1** is not run yet.
